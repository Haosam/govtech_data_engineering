# Application Processing ETL Pipeline

## Overview

This project implements a simple data engineering ETL pipeline for processing membership applications.

The pipeline reads application CSV files, validates each application against a set of business rules, separates successful and failed applications, transforms successful records into the required output format, and writes the resulting datasets into separate output folders.

The processing logic is written in Python using Pandas. An Apache Airflow DAG is also included to demonstrate how the pipeline can be scheduled to run hourly.

## Input Data

The input CSV is expected to contain the following fields:

```text
name
email
date_of_birth
mobile_no
```

Example:

```csv
name,email,date_of_birth,mobile_no
Mr. Joshua Ellis Jr.,Joshua_Ellis@example.com,1996-02-26,81234567
Jane Tan,jane@example.net,20/03/1990,92345678
```

---

## Validation Rules

Applications are considered unsuccessful if any of the following conditions are met:

1. The applicant does not have a name.
2. The mobile number is not exactly 8 digits.
3. The date of birth cannot be parsed.
4. The applicant is below 18 years old as of 1 January 2022.
5. The email address does not follow the expected structure:

```text
<something>@<something>.<something>
```

Failed applications are written to the failed output dataset with a `failure_reason` column.

An application may contain more than one failure reason.

Example:

```text
missing_name;invalid_mobile;invalid_email
```

---

## Name Cleaning

Names are cleaned before further processing.

Common titles such as the following are removed:

```text
Mr.
Mrs.
Ms.
Miss
Dr.
Prof.
Sir
Madam
```

Professional or academic credentials at the end of names are also removed where applicable, including:

```text
MD
DDS
PhD
DVM
DO
```

The cleaned name is then split into:

```text
first_name
last_name
```

---

## Date Processing

The pipeline supports multiple input date formats, including:

```text
YYYY-MM-DD
YYYY/MM/DD
DD-MM-YYYY
DD/MM/YYYY
```

Successful application dates are converted into:

```text
YYYYMMDD
```

Example:

```text
1996-02-26
```

becomes:

```text
19960226
```

---

## Age Validation

Applicants must be at least 18 years old as of:

```text
1 January 2022
```

Successful applications receive an additional field:

```text
above_18
```

which indicates whether the applicant satisfies the age requirement.

---

## Membership ID

Each successful applicant receives a generated membership ID.

The format is:

```text
<last_name>_<hash>
```

The hash is generated by:

1. Converting the applicant's birthday into `YYYYMMDD`.
2. Generating a SHA256 hash from the formatted birthday.
3. Taking the first 5 characters of the SHA256 hash.

Example:

```text
Ellis_a1b2c
```

The membership ID generation therefore follows the structure:

```text
last_name + "_" + SHA256(YYYYMMDD)[:5]
```

## Output

Successful and failed applications are written separately.

Example:

```text
data/
├── successful/
│   └── applications_dataset_1_successful.csv
│
└── failed/
    └── applications_dataset_1_failed.csv
```

### Successful Output

Successful applications include transformed fields such as:

```text
first_name
last_name
date_of_birth
above_18
membership_id
```

### Failed Output

Failed applications retain their original information together with:

```text
failure_reason
```

## Running Locally

The transformation logic can be tested without Apache Airflow.

Install the required Python packages:

```bash
pip install -r requirements.txt
```

Then run:

```bash
python main.py
```

`main.py` reads an application dataset, applies the ETL processing logic, and writes successful and failed application CSV files.

## Apache Airflow

The project includes an Airflow DAG located at:

```text
dags/pipeline.py
```

The DAG is configured to run:

```text
Hourly
```

using:

```python
schedule="@hourly"
```

The DAG calls the ETL processing function located in:

```text
dags/application_etl.py
```

The intended workflow is:

```text
Incoming CSV
     |
     v
Airflow Hourly DAG
     |
     v
Application Validation
     |
     +---------------------+
     |                     |
     v                     v
Successful             Failed
Applications           Applications
     |                     |
     v                     v
data/successful/       data/failed/
```

Airflow is not required to run `main.py` for local testing.

## Design Notes

The ETL transformation logic is separated from the Airflow DAG.

This allows the same processing code to be:

- tested locally using `main.py`;
- executed by Airflow;
- reused by other orchestration tools if required.

The Airflow DAG is responsible for orchestration and scheduling, while `application_etl.py` contains the business and transformation logic.

For a production implementation, additional improvements could include:

- archiving processed input files;
- stronger idempotency controls;
- structured logging;
- schema validation;
- automated testing;
- error monitoring;
- database or object-storage integration;
- configurable input and output locations.
